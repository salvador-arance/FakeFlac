title: Analyse a folder from the command line with the app's engine (user CLI)
priority: medium
milestone: H3
status: draft
---

A user can analyse a folder from the command line and get **the same results as the app** for the same files and parameters: the same `DetectionParams`, the same `TrackAnalysis` per track and the same result cache. The output can be piped (CSV or JSON on stdout, progress on stderr) and the exit code says whether any track is `Fake`.

Measurable acceptance (to be fixed at G1 of its spec):
- **Same engine.** For every fixture, the CLI's verdict, cutoff, estimate, reasons and evidence equal the app's (`analyze_folder` in `fakeflac-core` is the single use case).
- **Output.** CSV identical to the app's export (`csv-export.md`); JSON with a versioned schema generated from the Rust types (S3), never hand-written.
- **Exit codes and streams.** Fixed exit codes (none `Fake`, at least one `Fake`, usage error, I/O error); nothing but results on stdout.
- **Guarantees.** Read-only (RNF-05), no network (RNF-03, the privacy lint covers the new crate), a corrupt file never stops the run (RNF-04), memory budget (RNF-02).
- **Distribution.** Shipped with the release (RNF-11) within the size gate (RNF-06).

Source: owner's decision of 2026-11-20 (H3 extension, #184), from the comparison with AudioAuditor 2.0.0, whose CLI shares its GUI's engine. The planning document already lists `fakeflac-cli` as a future second input adapter (crate table). Issue #202.

Spec: pending (`/new-spec RF-18`). Needs an ADR for the new crate and any argument-parsing dependency (ask before adding one). Open questions in #202: platforms beyond Windows (RNF-07), a cache shared with the app (ADR-0044), and whether `census` moves from the dev-only calibration tool.
