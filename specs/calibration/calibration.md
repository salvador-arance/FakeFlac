# Calibration and acceptance tool (`just accept`, `/calibrate`)

> A dev-only binary turns the user's music library into a corpus with known truth, runs the Rust detector on it with one or more `DetectionParams` files, and writes a confusion-matrix report. `/calibrate` also searches a grid of rule parameters on the `tune` split and proposes a new `detection-params.vN.toml`, which it never commits. Where the tool lives and its dependencies: ADR-0036.

Related specs: [inputs.md](inputs.md) (`trusted.txt`, `confirmed.txt`, `labels.csv`, split) · [generation.md](generation.md) (transcodes, features cache) · [evaluation.md](evaluation.md) (run outputs, comparison, grid search) · [sample-corpus.md](sample-corpus.md) (CI corpus) · [lossy.md](lossy.md) (lossy files, RF-15) · scenarios: `specs/features/calibration.feature`, `specs/features/calibration-lossy.feature`.

### Calibrating against the shipped detection (G1 decisions, owner, 2026-11-02)

The app runs detection v8 (`DetectionParams::default()` equals `detection-params.v8.toml`, lossy-source.md section 12.5), but `just accept` and `just calibrate` defaulted to v2 and grid v1 (baseline v2). A default `/calibrate` run therefore tuned the v2 rule family and compared two files that the app does not use: its proposal drops `[full_band]`, `[edge]` and `[lossy]`. Searching from v4 or later was blocked by rules.md Q10 (no feasible point).

**Measured before G1.** Conditions: the local corpus as revised by the owner on 2026-11-02, `calibration.v1.toml` (its lossless settings are those of the default `calibration.v2.toml`), and an 81-point probe grid with `grid_version = 2`, because the current tool rejects 3. The probe had the v8 baseline, `must_catch` `cbr128` and `cbr192`, the default weights, and the values `full_band.min_level_db` −80/−70/−60, `full_band.min_burst_db` 2/3/4, `verdict.gap_fake_db` 5/6/7 and `verdict.step_fake_db` 9/10/11. Figures from `summary.md`.
- **Corpus:** the classes are `primary` 66 tracks / 5 albums, `reviewed` 632 / 54, `clean` 563 / 41 and `reference` 785 / 68, with 2040 transcode sources per setting.
- **Feasibility:** with the v8 baseline, all 81 points (the baseline among them) are infeasible. The baseline has 1 detectable `cbr128` `Real` in `tune` (2 in `holdout`; `cbr192`: 0), and every confirmed fake is `Fake`. Each of the 10 best points has exactly 1 such `Real`, so no point changes that count, and the search proposes nothing.
- **Cost:** costs range from 2364.9 at the baseline to 2338.4 at the best point. The cost is dominated by `v0` and `aac256` false negatives (2190 `Real` tune positives at every one of the 10 best points). This is a known limitation (evaluation.md section 7) that no point changes.

**Why no point changes a `Real` verdict** (rules.md section 3):
- `full_band.*` and `gap_fake_db` act only through V3 and the `FullBand` guard. When V3 stops firing, V5 (`G ≥ gap_suspicious_db`, and `gap_suspicious_db ≤ gap_fake_db`) gives `Suspicious`.
- `FullBand` never removes V4, because inside the lossy range it needs `D < max_lossy_step_db` (3 dB) and V4 needs `D ≥ step_fake_db`.
- So these keys only move `Fake` ↔ `Suspicious`. False negatives, `must_catch Real` and confirmed fakes `Real` are the same at every point.
- With 0 `Fake` on `primary`, the only way such a point lowers the cost is to turn guarded `Suspicious` positives into `Fake`, mostly `v0` and `aac256`. Their guard is intended (rules.md section 6). This is why OQ-24 takes them out of the cost.

**Out of this PR** (recorded so that G1 sees them):
- The `cbr128` transcode that v8 misses (rules.md Q10 lists the alternatives: review it, refine the undetectable rule, or search `lossy_min_cutoff_hz`).
- Whether T2 and T3 count undetectable transcodes (rules.md Q9).
- The 15 confirmed fakes are all in `tune`, so no `holdout` figure checks known-truth fakes (OQ-7; the report warns about it).
- Searching parameters that move `Real` verdicts.

### Acceptance targets and undetectable transcodes (owner decisions, 2026-11-02 and 2026-11-14; draft 2026-11-14; G1 pending)

The L5 run with v8 (`20261102T170123Z`, defaults: `calibration.v2.toml`, `detection-params.v8.toml`) reports T1 `PASS` (0), T2 `FAIL` (5) and T3 `FAIL` (8). Until now, targets have counted `Real` over **every** generated row of their settings, undetectable transcodes included, while every rate leaves those out (rules.md Q9). The `Real` rows behind the two failures were diagnosed locally with v8, and two `cbr128` cases were encoded again with the config's recipe. Only aggregates and measurements appear here (ADR-0022).

- **T2: 5 rows, 4 `cbr128` and 1 `cbr192`.**
  - 2 are undetectable (criterion `extent`): the `cbr192` row and one `cbr128` row. Their source band ends near 11.85 kHz.
  - 1 `cbr128` row is a quiet solo-piano source:
    - Above 15 kHz the source is already at the digital floor, with a mean level of about −91 dB in 15–16, 17–19 and 19.5–21.5 kHz, and the transcode is identical there.
    - It counts as detectable: the band measures are relative to a quiet reference band, so the floor counts as content and `fe` is Nyquist.
  - 1 `cbr128` row is a loud track whose low-pass is masked by clipping in the 16-bit decode: `fs` 16050 Hz, `fe` 22050 Hz, `D` 5.49 dB (rules.md section 6).
  - 1 `cbr128` row has its step at 14450 Hz, 50 Hz below `lossy_min_cutoff_hz`, with `D` 8.07 dB (rules.md section 6).
- **T3: 8 `cbr320` rows.**
  - 3 are undetectable.
  - 5 are detectable, with `fs` 19350–20350 Hz, `D` 4.5–11.6 dB and `G` ≤ 2.3 dB; 3 are in `tune` and 2 in `holdout`. This is the zone of the genuine purchased discs (rules.md, "Why v2 was replaced").

**Owner decisions (final):**
1. **Q9:** T2 and T3 exclude undetectable transcodes, like the rates. The undetectable rule keeps its two criteria, `extent` and `hf drop`, written down as the tool applies them (evaluation.md section 2, OQ-30).
   - **Revised on 2026-11-14, after measurement.** The decision of 2026-11-02 also widened "undetectable" with a third, absolute **floor** criterion for the piano case. The owner removed it: the measurement shows that none of the measured criteria on the absolute level of the source above `lowpass_hz` (the highest band level and 12 window-mean variants) makes the piano source undetectable without also making transcodes that v8 catches undetectable (rules.md section 6, "Calibration findings with v8", gives the figures).
   - The quiet solo-piano transcode is therefore a **third known limitation** (rules.md section 6). It stays detectable and counts in T2.
2. **Clipping:** the clipping-masked `cbr128` transcode is a known limitation (rules.md section 6). A clipping-aware measure is a later detection spec.
3. **14450 Hz step:** a known limitation. `lossy_min_cutoff_hz` stays 14500 Hz, because moving it for one track would be fitting the corpus.
4. **T3** becomes a rate bound: at most 1.0 % `Real` over detectable `cbr320` transcodes, instead of a count of 0.

This is a calibration change (RP-11): no `DetectionParams` value, rule, contract or `algorithm_version` changes.

### Authentic releases mastered from lossy material (owner decision, 2026-11-14; draft 2026-11-14; G1 pending)

**Evidence** (whole-library run of the release app with detection v8 on 2026-11-14; aggregates only, ADR-0022). 501 of 4,233 lossless tracks were `Fake`. Of the 135 albums with at least one lossless `Fake`, 6 have a CD rip log. In 5 of them, 35 `Fake` tracks match the log's copy CRC bit for bit; 8 of those (2 albums) are also verified by AccurateRip or CTDB. Their evidence is strong, not marginal: one database-verified album has 6 of 11 tracks `Fake` by V3 with `G` from 14 to 35 dB, and one log-matched album has 16 of 16 tracks `Fake` with `G` about 50 dB and `D` about 30 dB. No threshold change clears them. Today inputs.md section 1.5 maps the origins `cd-log` and `accuraterip` to class `primary`, so listing these discs as trusted would make T1 fail (8 tracks with database proof) and, worse, would use lossy-mastered audio as a lossless source for transcodes and as a tuning negative.

**Owner decision (2026-11-14, final; not an open question).** A verified, untouched copy of a published release whose audio carries lossy traces because the release's own master was made from lossy material goes into the corpus as **its own class**, not as `primary` or as a trusted negative. T1 keeps its meaning and does not count these tracks. The limitation is measured and reported, not hidden.

**Proposal.** A new `confirmed.txt` kind `lossy-master` (inputs.md section 2.1), labelled `truth`, `class` `lossy_master` and `origin` `confirmed_lossy_master` (inputs.md section 3), split in a stratum of its own (inputs.md section 4), never a source (generation.md section 1) and never tuning data (evaluation.md section 7), and reported in evaluation.md section 10. The known limitation goes into rules.md section 6 as a marked addition. No `DetectionParams` value, rule, `algorithm_version`, config file or contract changes.

## 1. Scope

In: WAV and FLAC negatives, transcodes to FLAC, the v2 rule family (`specs/detection/rules.md`: v2 files, v3 files, which add the optional `[full_band]` section, and v4 files, which add the optional `full_band.max_lossy_step_db`), confusion matrices, margins, parameter comparison, grid search over rule parameters.

Lossy-format detection (RF-15) is **in** since [lossy.md](lossy.md): lossy files as labelled tracks (honest encodes, cascades, the user's lossy labels), chains of versions of one master, split units, and lossy tables kept apart from every lossless figure.

Out (the design must allow adding them later without changing the file formats): upsamples (RF-12: a new `setting` kind), file integrity, grid search over `[lossy]` values, and any change to the thresholds. New parameters go in their own spec PR.

The calibration tool does not change the app's contract (`specs/contracts/commands.md`); its version 3 (lossy formats) comes from detection v5 (`specs/detection/lossy-source.md`, ADR-0041), not from the tool. The tool's contract is its command line (section 2) and its files ([inputs.md](inputs.md), [generation.md](generation.md), [evaluation.md](evaluation.md)).

## 2. Commands

Every command goes through `just` (ADR-0019). The recipes run the release build of the binary `fakeflac-calibrate` (ADR-0036) from the repository root.

| Recipe | Binary call | What it does |
|---|---|---|
| `just accept *ARGS` | `fakeflac-calibrate accept [--params FILE]… [--config FILE] [--no-generate]` | Prepare (section 4) and evaluate every `--params` file. Writes one report folder. |
| `just calibrate *ARGS` | `fakeflac-calibrate calibrate [--grid FILE] [--config FILE]` | Prepare, evaluate the baseline, run the grid search on `tune`, evaluate the proposal on `tune` and `holdout`, and write the proposed params file into the report folder. |
| `just privacy-check` | `fakeflac-calibrate privacy-check [--base REF]` | Section 6. Default `REF` is `main`. |

- `--params` may be repeated. The default is the params file the app ships, equal to `DetectionParams::default()`: `specs/detection/detection-params.v8.toml` since detection v8 (OQ-18). The first file is the **baseline** that the others are compared against. A params file may live outside the repository (for example a proposal in `FAKEFLAC_CALIBRATION/reports/…`).
- `--config` defaults to `specs/calibration/calibration.v5.toml` (OQ-29): `calibration.v2.toml` with the acceptance targets of version 2 ([evaluation.md](evaluation.md) section 6), where v2 is v1 plus the lossy entries of RF-15 ([lossy.md](lossy.md) section 8). `calibration.v1.toml` to `calibration.v4.toml` stay loadable. `--grid` defaults to `specs/calibration/calibrate-grid.v3.toml` (OQ-18 to OQ-24). That grid has no `baseline` key, so it searches from the default params file; a grid without `baseline` always does. `calibration.v3.toml` (v2 plus four settings decoded to 24 bits, [generation.md](generation.md) section 2) is not the default: the acceptance run of detection v6 passes it explicitly (rules.md section 8). The earlier grids stay loadable: `calibrate-grid.v1.toml` (baseline v2) and `calibrate-grid.v2.toml` (baseline v3, `[full_band]`). The default files (params, config and grid) and a relative `baseline` in a grid file are resolved against the repository root (section 3), not the current folder. Without a repository they are read relative to the current folder, as today. A path given on the command line is used as given. The sample corpus expectations ([sample-corpus.md](sample-corpus.md)) pass `detection-params.v2.toml` explicitly, so the new defaults do not change them; the acceptance runs of detection v4 and later pass their params files explicitly too (rules.md sections 7 and 8).
- `--no-generate` evaluates the labelled tracks that already have cached spectra and skips missing generated entries. It leaves `labels.csv` untouched. The report counts them as "not generated".
- None of these recipes is part of `just ci`. The CI-runnable acceptance is a `cargo test` of the tool on the sample corpus ([sample-corpus.md](sample-corpus.md)).

### Exit codes

| Code | When | Output written |
|---|---|---|
| 0 | Run finished (also when acceptance targets are missed, OQ-12, or the grid search finds no feasible point) | report folder |
| 1 | Internal error (a bug) | nothing new, except cache lines already appended |
| 2 | Input or configuration error: missing or invalid environment variable, error in `trusted.txt` or `confirmed.txt`, `library_root` mismatch, invalid params, config or grid file, unsupported params file (v1, OQ-1), no trusted tracks | nothing |
| 3 | External tool error: ffmpeg not found, or `ffmpeg -version` fails, when a transcode is needed | nothing new, except cache lines already appended |

A decoding error on one track never stops the run (RNF-04): the track gets the verdict `Error` and is counted in the `Error` column.

## 3. Environment and containment

| Variable | Required | Rule |
|---|---|---|
| `FAKEFLAC_CORPUS` | yes | Absolute path of an existing, readable folder. Not inside the repository. |
| `FAKEFLAC_CALIBRATION` | yes | Absolute path of an existing folder. Not inside the repository, not inside `FAKEFLAC_CORPUS`, and `FAKEFLAC_CORPUS` not inside it. |
| `FAKEFLAC_FFMPEG` | no | Path of the ffmpeg executable. Default: `ffmpeg` on `PATH`. |

- The repository is the output of `git rev-parse --show-toplevel` run from the current folder. If that fails (not in a git checkout), the "not inside the repository" checks are skipped.
- The checks run first, before any file is read or written. A missing variable gives exit 2 and `error: FAKEFLAC_CORPUS is not set (define it in .claude/settings.local.json, key "env")`. When both are missing, both are named. "Inside" is decided on canonical paths.
- The binary strictly refuses to start (exit 2) if `FAKEFLAC_CALIBRATION` is inside `FAKEFLAC_CORPUS`, if `FAKEFLAC_CALIBRATION` is inside the repository, or if `FAKEFLAC_CORPUS` is inside `FAKEFLAC_CALIBRATION`.
- The variables are set by the user in `.claude/settings.local.json` (not versioned), never by an agent.
- **Read-only corpus (RNF-05, ADR-0022).** Files under `FAKEFLAC_CORPUS` are opened strictly read-only (`File::open` without write access) for decoding, and passed to ffmpeg as inputs (`-i`). Nothing is created, changed or deleted there.
- **Writes** go only inside `FAKEFLAC_CALIBRATION`: `labels.csv`, `generated/`, `features/` and `reports/`. Files are written to a temporary name in the same folder and then renamed. The tool deletes only files it created in `generated/`.
- The tool never runs a git command that writes. It runs only `git rev-parse --show-toplevel` (the repository check above), `git rev-parse HEAD` (recorded in the report) and, for `privacy-check`, `git diff`.

## 4. Pipeline

```
check env → parse trusted.txt, confirmed.txt → enumerate tracks → album ids + split
 → extract spectra of corpus tracks (cache)        → generate transcodes (cache by recipe)
 → extract spectra of generated tracks (cache)      → write labels.csv
 → for each params file: measure + decide on cached spectra → report
 → (calibrate) grid search on tune → proposal → report
```

- Spectra are produced by `fakeflac_audio::SymphoniaAnalyzer` (`SpectrumAnalyzer::analyze`). Measurements and verdicts come from `fakeflac_core::detect::{measure, decide, cutoff_estimate}` and the silent-track rule of `detect` (rules.md section 1.6). The tool does not reimplement any detection step (ADR-0036).
- Corpus tracks are enumerated with `fakeflac_fs::WalkDirScanner` (hidden entries skipped, links not followed). Only FLAC and WAV count as trusted or confirmed tracks, except where RF-15 adds MP3, M4A and Opus files ([lossy.md](lossy.md) section 1.1).
- Extraction and transcoding run on `cores − 1` std threads. Results are sorted (section "Determinism") so the thread count never changes any output.
- **Determinism.** With the same inputs, cache and parameters, two runs produce byte-identical `labels.csv`, `tracks.csv` and report files, except for the run id, the date and the cache statistics.

## 5. `/calibrate` skill

A Claude Code skill (`.claude/skills/calibrate/`, written in the implementation PR) that:

1. Runs `just calibrate` (with `--grid` if the user gives one). If the exit code is 2 or 3 it shows the message and stops.
2. Shows the user `summary.md` of the new report folder. It may read `report.md` locally to answer questions, but only text from `summary.md` may be copied into a repository file, a commit or a PR.
3. Gives the proposal's location as `FAKEFLAC_CALIBRATION/reports/<run>/detection-params.vN.toml`. It never copies the file into `specs/`, never commits and never opens a PR. A proposal enters the repository only through a separate spec PR (G1), written from `summary.md`.

## 6. Privacy (ADR-0022)

- Outputs with corpus names or paths (`labels.csv`, `report.md`, `tracks.csv`) stay in `FAKEFLAC_CALIBRATION`. Paths in them are relative to `FAKEFLAC_CORPUS` or to `generated/`. **No output contains an absolute path** of either root.
- `summary.md` is the only output written for PRs. It contains counts, rates, intervals, setting ids, origin names, params file **names** (no folder) with content hashes, encoder versions, and watch ids (`W1`…) with their measurements. It never contains an album id, a folder name, a file name or a note from `trusted.txt`/`confirmed.txt`.
- `just privacy-check` lists every file changed between `--base` and `HEAD` (`git diff --name-only REF...HEAD`) and searches their contents, ignoring case, for: both root paths (with `\` and `/`); and every folder name and file stem of the labelled corpus tracks with 8 or more characters, excluding any pattern listed in an unversioned exceptions file `privacy-exceptions.txt` (or `.privacy-exceptions` in the repository root or in `FAKEFLAC_CALIBRATION`). This allows excluding common words (e.g. 'Standard', 'Live') that might cause false alarms. It prints `file:line` for each match and exits 1 if there is any match or if a file could not be checked, 0 otherwise. It needs the two variables, like `accept`.
